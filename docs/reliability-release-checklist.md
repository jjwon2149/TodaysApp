# 신뢰성 배포 검증 및 사용자 조사

## 현재 판정
정식 출시 보류: 구현, 최종 자동 테스트 65개, Debug/Release 시뮬레이터 빌드와 독립 코드 검토는 완료했다. 후속 요청에 따라 1.0.5(7) 실기기 아카이브와 TestFlight 업로드도 성공했으며 Apple 처리 시작을 확인했다. 실제 CloudKit 두 기기·TestFlight 설치 후 동작·전체 UI/업데이트 검증 후 정식 출시를 재판정한다. 상세 증거는 `reliability-release-results.md`를 참조한다.

## 증거 기록 형식
각 항목에 빌드/커밋, 기기·OS, 기존 데이터 상태, 재현 절차, 기대/실제 결과, PASS/FAIL/미실행과 증거 위치를 남긴다. 테스트 전용 사진만 사용하며 계정 정보·사진 내용·토큰은 기록하지 않는다.

## 출시 필수 체크
- [ ] 신규 동기화: 원본과 썸네일을 두 기기에서 확인
- [ ] 기록 정보 업로드 후 사진 전송 실패 → 앱 재실행 → 재시도로 복구
- [ ] 원본 성공/썸네일 실패, 다운로드 중단을 각각 복구
- [ ] 과거 빌드가 만든 부분 동기화를 수정 시간이 같아도 복구
- [ ] 정상 반복 동기화는 중복 기록/불필요 전송 없음
- [ ] 두 기기 사진 교체·삭제, 동기화 도중 편집에서 최신 상태 보존
- [ ] 부분 실패 시 완료로 표시하지 않으며 기존 정상 사진 보존
- [ ] 미로그인/동기화 끔/오프라인에서 로컬 저장 유지
- [ ] 홈 최초 읽기 실패와 갱신 실패를 빈 기록과 구분, 재시도로 정상 회복
- [ ] 오늘 기록 확인 실패 시 신규 작성으로 기존 사진을 덮어쓰지 않음
- [ ] 신규 저장·기록 수정·스트릭 조회 실패의 완료 문구가 실제 결과와 일치
- [ ] 기존 배포 데이터로 업데이트 후 사진·메모·스트릭 보존
- [ ] 카메라/사진 선택/캘린더/알림/위젯/백업 내보내기 회귀
- [ ] 한국어·영어·일본어, 큰 글씨, VoiceOver에서 안내·버튼 확인
- [ ] 앱과 위젯 빌드, 전체 XCTest, TestFlight 실제 CloudKit 환경 확인

## 사용자 검증 운영
담당: 프로젝트 담당자가 참여 모집과 관찰을 진행하며 결과 담당자를 실행 전에 기입한다. 현재 모집/연락/관찰은 미실행이다.

1. 동의한 참여자 5~10명을 모집하고 별도 조사용 번호를 부여한다. 앱에는 분석 SDK나 조사 식별자를 넣지 않는다.
2. 첫 실행에서 도움 없이 첫 사진을 저장하도록 관찰한다. 성공 여부, 막힌 단계와 이유, 도움 제공 여부를 기록한다. 개인 사진/메모를 요구하지 않는다.
3. 첫 저장 다음 날과 7일 뒤, 다시 기록했는지와 이유를 묻는다. 앱 열기와 실제 기록 저장을 구분한다. 사진 증빙 제출은 요구하지 않는다.
4. 분모는 각 관찰일이 도래한 첫 저장 참여자 수로 한다. 응답자 수, 재기록 자기보고 수, 무응답 수를 분리한다. 무응답을 성공/실패로 단정하지 않는다.
5. 소규모 자기보고 조사라는 한계를 명시하고 실제 전체 유지율로 표현하지 않는다. 개선을 주장하려면 동일한 조건의 비교 자료가 필요하다.
6. 결과에 따라 미션 다양화 또는 기록 회고 중 다음 실험 하나를 선택한다. D7 관찰 전 완료 처리하지 않는다.

| 조사 번호 | 첫 저장일 | 도움 없이 저장 | 막힌 단계/이유 | D1 응답/재기록 | D7 응답/재기록 | 재방문/이탈 이유 |
|---|---|---|---|---|---|---|
| 미실행 | — | — | — | — | — | — |

연락처는 이 저장소에 보관하지 않는다. 참여 동의와 연락은 담당자가 별도로 관리한다. 출시용 GrowthEventLogger는 계속 no-op으로 유지한다.

## 출시 순서와 중단 조건
자동/수동 검증 → TestFlight → 두 기기 검증과 첫 사용 관찰 → 정식 출시 판단 → D1/D7 조사. 버전/빌드는 실제 배포 단계에서 기존 번호를 조회한 후 정한다.
사진 누락, 삭제 부활, 기존 데이터 손실, 재시도 불능이 남으면 출시하지 않는다. 출시 후 발견되면 배포 확대를 중단하고 데이터 보존 수정 빌드를 준비한다. 즉시 앱 다운그레이드를 전제로 하지 않는다.
